🌟 ¿Qué es MockHive?

              

                MockHive es la plataforma de computación cloud efímera y distribuida de Terra. Convierte el tiempo de computación gratuito de GitHub Actions en servidores virtuales interactivos (HiveNodes), máquinas de estado serverless (Waggles), micro-funciones aisladas (PollenPods) y clusters paralelos Map-Reduce (HiveGrid) sin servidores dedicados ni costes de suscripción.
              

            


            

              
🏰 HiveNodes: Servidores Virtuales, Web Terminal & SSH

              

                Un HiveNode es una máquina virtual Ubuntu completa ejecutada sobre un runner de GitHub Actions con persistencia de archivos en /mockhive/data. Dispone de dos formas de conexión:
              

              
              

                

                  
🌐 Vía 1: Web Terminal Instantánea (Recomendada - Cero Instalación)

                  

                    Pulsa el botón 🚀 Abrir en Navegador en la tarjeta del servidor. Entrarás directamente a una terminal xterm interactiva completa con zsh/bash, soporte para copiar/pegar, colores y permisos de sudo sin instalar ningún cliente.
                  

                


                

                  
💻 Vía 2: SSH Nativo desde PowerShell / Terminal / VS Code

                  

                    Para evitar que los routers domésticos y firewalls bloqueen los puertos TCP no estándar, MockHive tuneliza el tráfico SSH a través del puerto 443 (HTTPS) mediante Cloudflare Tunnel.
                  

                  
📦 Requisito Único (Instalar binario de Cloudflare):

                  
# En Windows (PowerShell):
winget install --id Cloudflare.cloudflared

# En macOS (Homebrew):
brew install cloudflare/cloudflare/cloudflared

# En Linux (Debian / Ubuntu):
sudo apt-get install cloudflared

                  
⚡ Conexión:

                  

                    Copia el comando SSH de tu nodo (que incluye el ProxyCommand de Cloudflare) y pégalo en tu terminal. Te solicitará la Contraseña SSH configurada en el formulario (por defecto: mockhive2026).
                  

                

              

            


            

              
⚠️ Modo 24/7 Lazarus Relay & ToS de GitHub

              

                El modo 24/7 utiliza relevos automáticos (relays) antes de las 6 horas de límite del runner de GitHub. Úsalo con moderación y exclusivamente para servidores que realmente requieran continuidad. Para desarrollo y tareas puntuales, utiliza siempre el modo TTL Efímero.
              

            


            

              
🐝 Waggles: State Machines & Modos de Ejecución

              

                Las Waggles son el equivalente Serverless a AWS Step Functions a coste $0. Permiten orquestar flujos de trabajo declarativos en formato ASL (Amazon States Language) con estados Task, Choice, Pass, Wait, Succeed y Fail.
              


              
⚡ Comparativa de Modos de Ejecución:

              

                

                  
🌐 Modo 1: Navegador (client_browser)

                  
    
                    
  • Arranque: Instantáneo (0 ms de espera).
    • 
                    
  • Entorno: Motor JavaScript en memoria del navegador.
    • 
                    
  • Capacidades: Ejecuta el DAG, evalúa ramas lógicas Choice, resuelve $.JSONPath y hace peticiones de red fetch() a APIs públicas o locales.
    • 
                    
  • Ideal para: Desarrollo rápido, validación de lógica de flujo y prototipado sin gastar minutos de CI.
    • 
                  

                


                

                  
☁️ Modo 2: Cloud Runner (cloud_runner)

                  
    
                    
  • Arranque: ~15-25 segundos (aprovisionamiento de contenedor).
    • 
                    
  • Entorno: Máquina Virtual Ubuntu 24.04 LTS real en GitHub Actions (7 GB RAM, 2 vCPU).
    • 
                    
  • Capacidades: Acceso completo a terminal Linux, Node.js 20, Python 3, AWS CLI, subida a S3/R2, bases de datos y persistencia automática del resultado en tu repositorio.
    • 
                    
  • Ideal para: Producción, procesamiento de datos pesados, pipelines de CI/CD reales y tareas con credenciales seguras.
    • 
                  

                

              

            


            

              
💡 Buenas y Malas Prácticas

              

                

                  
✔️ Buenas Prácticas

                  
    
                    
  • Monta almacenamiento persistente en /mockhive/data para no perder archivos en tus HiveNodes.
    • 
                    
  • Utiliza el modo Navegador para probar la lógica de tus Waggles antes de despacharlas a un Cloud Runner.
    • 
                    
  • Usa conectores tipo Storage para desacoplar las credenciales de S3 o Rolla de la lógica de tus DAGs.
    • 
                    
  • Aprovecha los estados Choice para crear compuertas de seguridad automáticas basadas en scores o métricas.
    • 
                  

                

                

                  
❌ Malas Prácticas

                  
    
                    
  • No dejes corriendo múltiples servidores 24/7 sin supervisión para evitar consumir tu cuota de Actions.
    • 
                    
  • No guardes contraseñas en texto plano; utiliza Secrets de GitHub o campos de Auth en tus Conectores.
    • 
                    
  • No uses bucles infinitos dentro de scripts inline sin una condición de salida garantizada.
    • 
                  

                

              

            


            

              
❓ Preguntas Frecuentes (FAQ) & Resolución de Dudas

              
              

                

                  
¿Las Waggles ejecutan y crean recursos de forma 100% real como AWS Step Functions?

                  

                    Sí. El motor de estados (grafo de dependencias, variables $.path, bifurcaciones Choice y reintentos) opera exactamente bajo el estándar ASL de AWS. Cuando se ejecuta en modo Cloud Runner, una máquina virtual Ubuntu real ejecuta las acciones, lanza llamadas de red TLS y puede crear o modificar recursos externos en cualquier proveedor de la nube.
                  

                


                

                  
¿Puedo subir archivos y escribir en AWS S3, Cloudflare R2 o Bases de Datos?

                  

                    Totalmente. Creas un conector de tipo Storage (S3) o HTTP con tus credenciales de acceso (Access Key ID, Secret Key o Token). El runner de GitHub Actions tiene conectividad abierta a internet y las librerías necesarias para ejecutar subidas de objetos (PutObject), inserciones en bases de datos o llamadas a webhooks.
                  

                


                

                  
¿Cómo cambian los parámetros según el Tipo de Conector?

                  

                    El formulario se adapta dinámicamente:
                    
• HTTP: Pide Base URL, Método HTTP, Tipo de Auth (Bearer, API Key) y Cabeceras JSON.
                    
• Storage: Pide Proveedor (Rolla-Ball, AWS S3 o GitHub Vault), Bucket/Ball ID y credenciales de acceso.
                    
• Code / Pod: Pide Runtime (JavaScript, Python 3, Bash), Timeout y el script de transformación en código puro.
                  

                


                

                  
¿Dónde se guardan mis configuraciones y resultados?

                  

                    Todo se sincroniza automáticamente en tu propio repositorio privado .mockhive-storage en GitHub mediante la Git Database API. No existe ningún servidor central propietario de Mockhive: la infraestructura es 100% tuya, privada y a coste $0.
                  

                


                

                  
¿Cómo paso datos entre estados consecutivos en una Waggle?

                  

                    Utiliza la propiedad "ResultPath": "$.nombreVariable" en el estado de origen. El resultado se inyectará en el contexto global $ y estará disponible en los siguientes estados usando referencias como "$.nombreVariable.propiedad".
